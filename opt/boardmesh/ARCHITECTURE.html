Architecture

Architecture

Intent

Boardmesh is no longer just a desktop GUI. It now has multiple delivery paths:

  • wxWidgets GUI
  • MCP server
  • WebSocket JSON-RPC runtime
  • CLI client
  • file-backed scene/session persistence

That means a pure MVC mental model is too narrow for the whole project. MVC still fits inside the GUI, but the overall system is better modeled as a hexagonal / clean architecture system:

  • the center owns board rules and session behavior
  • transport and UI layers translate requests into those behaviors
  • persistence and framework code stay at the edge

Why Not Global MVC

MVC works well for a single UI:

  • Model: state
  • View: widgets
  • Controller: event handlers

It breaks down when the same behavior must be reachable from:

  • GUI clicks
  • MCP tool calls
  • runtime JSON-RPC methods
  • CLI commands

In this project, CLI and MCP are not really "views". They are interface adapters that should call the same application behavior.

Current strengths

  • scene and persistence primitives already live in library modules
  • runtime transport contracts are already shared
  • GUI layout state is already extracted into a reusable module

Current weaknesses

  • application behavior is still concentrated in binaries
  • boardmesh-mcp.rs mixes transport, persistence, session logic, and board mutations
  • boardmesh.rs still mixes GUI view code with application behavior
  • adding new front doors risks duplicating business rules

Layer Responsibilities

Domain

Owns board rules and concepts:

  • scene objects
  • selection rules
  • geometry and hit testing
  • history semantics
  • session semantics

This layer should not know about:

  • wx widgets
  • MCP tools
  • WebSocket payloads
  • JSON file paths beyond abstract repository needs

Application Layer

Owns use cases:

  • add an object
  • delete an object
  • fill an object
  • switch sessions
  • replace the active scene
  • save or load a scene

This layer coordinates domain logic and persistence. It should be reusable from every delivery mechanism.

Interface Adapters

Translate external requests into application calls:

  • GUI event handlers
  • CLI command parsing
  • MCP tool handlers
  • runtime JSON-RPC handlers

Runtime-specific note:

  • websocket session attachment is client-local; one GUI window or CLI connection changing sessions must not mutate another client's active runtime board
  • runtime change notifications should be filtered to the session or scene each client attached to
  • one-shot runtime calls should carry an explicit session_id whenever they need to target a named session without a persistent attached websocket

Adapters should do translation and presentation, not own business logic.

Infrastructure

Implements technical details:

  • filesystem persistence
  • websocket transport
  • rmcp server transport
  • PNG rendering
  • wxWidgets widget rendering

MVC Inside The GUI

The GUI should still use an MVC-like split internally:

  • Model: GUI state snapshot plus application state projections
  • View: panels, canvas, toolbars, dialogs
  • Controller: event bindings that translate user actions into application commands

That is a local pattern inside the GUI adapter, not the architecture of the entire system.

Refactor Plan

Phase 1: Extract a shared application object

Create a reusable workspace/service object that owns:

  • active session id
  • session root
  • active scene path
  • active scene state

Move into it:

  • scene mutation operations
  • file-backed refresh/persist behavior
  • session activation and named-session bootstrap behavior

This reduces the amount of business logic embedded in boardmesh-mcp.rs.

Phase 2: Make MCP and runtime pure adapters

Move MCP/runtime handlers to:

  • decode request
  • call shared application service
  • map result to transport DTO
  • publish runtime notifications

At this point, MCP no longer owns board business rules.

Phase 3: Move GUI mutation behavior behind the same service

The GUI should stop mutating the scene directly for durable operations. Instead it should:

  • keep ephemeral draft state locally
  • call the shared application service for committed mutations
  • update history and selection views from application results

Phase 4: Harden the ports

Introduce explicit ports for:

  • scene repository
  • session repository
  • event publisher

That will allow future persistence backends without touching the core use cases.

First Refactor In This Round

This round starts Phase 1 by extracting a shared BoardWorkspace application object into the library and moving the MCP/runtime binary to use it.

That object is intentionally file-backed for now. It is not yet a full repository-driven clean architecture implementation, but it creates the correct seam:

  • binaries become thinner
  • core workflow becomes reusable
  • future GUI adoption becomes realistic
