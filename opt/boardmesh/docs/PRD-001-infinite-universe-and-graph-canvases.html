PRD-001: Infinite Universe and Graph Canvases

Summary

Boardmesh should evolve from a paint-like local whiteboard into an infinite spatial workspace that supports both freeform drawing and graph-aware structured diagrams.

The product model becomes:

  • one infinite Universe
  • multiple named bounded Canvases inside that universe
  • freeform objects that may live globally or belong to a canvas
  • graph-aware nodes and connectors that can bind to object anchors and follow moved shapes
  • a renderer architecture that works without GPU acceleration by default and can optionally use GL when available

The product should preserve the loose, sketch-first feel that makes Excalidraw compelling, while adding stronger structural semantics that Excalidraw does not emphasize.

Problem

The current Boardmesh scene model is strong enough for:

  • drawing freeform shapes
  • simple session persistence
  • GUI + MCP collaboration

It is not yet strong enough for:

  • infinite pan/zoom world navigation
  • named canvases inside one larger universe
  • object-bound connectors that follow moved shapes
  • graph-aware routing and splines
  • independent export and save behavior for canvases inside a larger world
  • a cleaner default workspace that prioritizes the board over every secondary panel

Vision

Boardmesh should feel like:

  • a sketchbook when you need speed
  • a diagram tool when you need structure
  • a shared visual workspace for humans and agents

The user should be able to:

  • pan and zoom across an effectively unbounded universe
  • define named canvases inside that universe
  • keep loose sketches outside canvases when useful
  • build graph-like diagrams inside canvases with connectors that stay attached
  • export one canvas or the whole universe
  • switch between a minimal focused view and richer secondary panels only when needed

Product Principles

  1. Freeform first Structured graph features must not make casual sketching feel heavy.

  2. World coordinates are the source of truth Camera state changes how the universe is viewed, not how objects are stored.

  3. Graph semantics are additive Paint objects and graph objects must coexist in the same universe.

  4. Testable geometry Routing, anchors, hit testing, viewport transforms, and bounds should live in pure Rust model code with unit tests.

  5. Backend-agnostic rendering Rendering should work without GL and optionally accelerate when GL is available.

  6. Context before clutter Secondary panels should not dominate the first-open experience.

  7. Human and agent parity where practical New universe, canvas, selection, connector, and object-management capabilities should be available through the GUI and exposed programmatically through MCP and the runtime CLI wherever the underlying action is meaningful without direct pointer gestures.

Core Concepts

Universe

The universe is the full infinite world document.

It owns:

  • canvases
  • drawable objects
  • graph nodes and connectors
  • selections
  • optional viewport presets

The universe can be saved and exported as a whole.

Canvas

A canvas is a named bounded region inside the universe.

A canvas has:

  • canvas_id
  • name
  • rect
  • visibility state
  • lock state
  • tags or metadata

A canvas can be:

  • moved
  • renamed
  • shown or hidden
  • exported independently
  • used as the active structured workspace

Objects may belong to a canvas or remain outside canvases in the universe.

Viewport

Viewport state defines how the user sees the universe.

It includes:

  • pan offset
  • zoom factor
  • optional fit or focus presets

Coordinate spaces:

  • world space
  • view space
  • screen space

All objects live in world space. Rendering and hit testing transform through the viewport.

Selection Context

Selection must resolve to more than raw selected ids.

Boardmesh needs a first-class selection-context model so humans and agents can ask about "this" or "these" and get:

  • primary selected object
  • selected set
  • object kind and semantic kind
  • canvas membership
  • connected objects
  • nearby objects
  • active canvas and selected canvases

This context must be derivable from pure model state and exposed through programmatic surfaces such as MCP and the runtime CLI.

Graph Layer

The graph layer is a mathematical model for:

  • nodes
  • anchors
  • ports
  • connectors
  • routing
  • spline geometry
  • hit areas

It should be pure model code and renderer-independent.

Connector

A connector is not just a painted line. It is a relation between endpoints.

Endpoint modes:

  • free point
  • bound to an object anchor

Connector kinds:

  • straight
  • orthogonal
  • spline

The connector path is resolved from current bindings, so it follows moved or resized objects.

Architecture

1. Graph Core

Create a mathematical graph layer that contains:

  • geometry primitives
  • anchors and ports
  • endpoint bindings
  • routed connector output
  • straight, orthogonal, and spline routing helpers
  • hit testing for connector geometry

This layer should have no GUI dependency and no GL dependency.

Recommended direction:

  • shared crate or isolated Boardmesh core module first
  • deterministic unit tests for routing and geometry

2. Scene Adapter

Boardmesh keeps a scene/domain layer that combines:

  • existing drawable objects
  • canvas membership
  • graph bindings
  • universe metadata

This layer adapts graph-core results into scene objects that the renderer can draw.

3. Renderer Interface

Define a renderer interface that supports:

  • lines
  • polylines
  • splines
  • polygons
  • circles
  • text
  • selection/highlight overlays
  • canvas frames
  • grid and viewport-aware decorations

Backends:

  • software renderer as the reference path
  • optional GL renderer when available

GL should be an optimization backend, not the base abstraction.

4. Interaction Layer

The GUI drives:

  • pan/zoom
  • selection
  • canvas focus
  • connector creation
  • endpoint rebinding
  • panel visibility

The GUI should not own the geometric truth of connectors or viewport math.

Interaction Model

Infinite Universe

Boardmesh should support:

  • wheel zoom centered on cursor
  • space-drag or middle-mouse pan
  • fit to content
  • zoom to selection
  • reset view
  • optional minimap later

Canvases

Boardmesh should support:

  • create named canvas
  • move canvas frame
  • show or hide canvas outlines
  • set active canvas
  • create objects into active canvas by default
  • optionally move member objects when moving a canvas

Connectors

Phase progression:

  1. straight bound connectors
  2. orthogonal connectors
  3. spline connectors
  4. richer anchors and editing affordances

Selection Tools

Selection should become a first-class interaction system rather than a thin side effect of clicking objects.

Boardmesh should support:

  • single select
  • additive multi-select
  • box select
  • lasso select later
  • select within active canvas
  • select connected graph neighborhood later
  • select by object kind or canvas later
  • keyboard-driven selection management

Selection should understand:

  • freeform drawables
  • graph-aware objects
  • canvas frames
  • connectors and their endpoints

Current implementation seam:

  • object selection is explicit scene state, with single-select, toggle/additive selection, and box-select helpers in model code
  • canvas selection is explicit universe state, with toggle and box-select helpers over canvas frames
  • richer lasso, neighborhood, and semantic selection builds on top of that state instead of replacing it

Selection state should support follow-on actions cleanly, including movement, grouping, canvas assignment, deletion, export, and z-order changes.

Selection Context for Agent Interaction

Boardmesh should treat selection as semantic context, not just UI highlight state.

When a human points at something and asks an agent about "this" or "these", the agent-facing system should be able to resolve:

  • the primary selected object
  • the full selected set
  • the semantic type of the selection
  • the canvas and universe context
  • nearby and connected objects
  • parent grouping or canvas membership
  • linked WorkMesh or Guildmesh references where present
  • a human-readable selection summary

This should lead to a first-class selection-context model, not only raw selected ids.

Directionally:

struct SelectionSnapshot {
    primary_selection_id: Option<String>,
    selected_ids: Vec<String>,
    selection_kind: SelectionKind,
    active_canvas_id: Option<String>,
    focus_bounds: Option<SceneRect>,
}

struct ObjectContext {
    object_id: String,
    object_kind: String,
    semantic_kind: Option<String>,
    canvas_id: Option<String>,
    group_id: Option<String>,
    linked_objects: Vec<String>,
    nearby_objects: Vec<String>,
    attributes: serde_json::Value,
}

struct SelectionContext {
    snapshot: SelectionSnapshot,
    primary: Option<ObjectContext>,
    selected: Vec<ObjectContext>,
    surroundings: Vec<ObjectContext>,
}

This context should be available to:

  • the GUI
  • MCP
  • runtime websocket methods
  • the runtime CLI

Object Management Tools

Boardmesh needs stronger object management than a paint-style whiteboard.

Object management should support:

  • duplicate
  • rename where meaningful
  • lock and unlock
  • hide and show
  • delete
  • clear selection
  • select all
  • group and ungroup later
  • bring forward / send backward / bring to front / send to back
  • assign to canvas / move between canvases
  • align and distribute later
  • inspect object metadata and relationships

The object-management layer should work across:

  • loose freeform shapes
  • text
  • graph nodes
  • connectors
  • canvas-scoped objects

Current implementation seam:

  • object visibility and lock state now live on DrawableObject in the scene model
  • model-facing operations currently cover duplicate, hide/show, lock/unlock, and z-order changes in SceneDocument
  • explicit canvas assignment and assignment clearing live in UniverseDocument
  • the workspace layer exposes the scene-backed management actions for persistence and runtime notification reuse
  • grouping, alignment, rename flows, and MCP/CLI parity remain later slices

Panels

The default layout should emphasize:

  • canvas
  • primary tool controls

Panels that should not dominate first open:

  • history
  • objects list
  • full session panel

The inspector should remain available, but secondary panes should be hidden or reduced by default until the user asks for them.

Save and Export Model

Boardmesh should support:

  • save full universe document
  • export full universe snapshot
  • export one named canvas
  • export current viewport
  • later: save reusable canvas templates

Canvas export should preserve the selected canvas bounds without requiring the universe to be split into separate files.

Current persistence contract:

  • Board documents remain JSON files.
  • The modern persisted shape is UniverseDocument.
  • Legacy scene-only JSON remains loadable and is migrated in memory through UniverseDocument::from_scene.
  • Canvas-scoped export derives a filtered SceneDocument from the universe instead of inventing a second unrelated persisted product format.

MCP and CLI Surface

The new Boardmesh architecture should not remain GUI-only.

Where operations are meaningful without direct pointer interaction, Boardmesh should expose them through:

  • MCP tools
  • runtime websocket methods
  • the runtime CLI surface

This applies in particular to:

  • canvas creation, listing, rename, move, visibility, and export
  • connector creation and rebinding
  • explicit selection queries and mutations
  • semantic selection-context queries for agent use
  • object management actions like duplicate, delete, lock, hide, reorder, and canvas assignment
  • viewport and focus actions where they make sense as programmatic commands

The GUI may still own gesture-heavy interactions, but the underlying domain actions should be callable programmatically.

Test Strategy

Unit Tests

Required for:

  • viewport world/screen transforms
  • canvas membership rules
  • anchor resolution
  • connector routing
  • spline control generation
  • bounds and hit testing

Integration Tests

Required for:

  • scene adapter correctness
  • persistence round-trips for universe documents
  • canvas export behavior
  • connector follow behavior when objects move
  • MCP/runtime/CLI parity for the new universe, selection, connector, and object-management actions where exposed

GUI/Smoke Tests

Required for:

  • pan and zoom behavior
  • selection workflows
  • default panel visibility
  • connector creation flow
  • canvas creation and focus flow
  • object management flows such as duplicate, lock, hide, delete, and z-order adjustments

Phased Roadmap

Phase 1: Foundation

  • universe + viewport model
  • panel simplification
  • richer selection tools
  • object management basics
  • named canvases
  • straight bound connectors

Phase 2: Structure

  • graph-core geometry layer
  • orthogonal routing
  • renderer abstraction
  • canvas export/focus workflows
  • stronger canvas-aware and graph-aware selection
  • grouping and z-order management

Phase 3: Power

  • spline routing
  • optional GL backend
  • minimap and viewport presets
  • richer anchor editing and graph tools
  • semantic graph selection and management workflows

Non-Goals For The First Slice

  • full BPMN/diagramming semantics
  • collaborative OT/CRDT editing
  • mandatory GPU rendering
  • replacing freeform sketching with rigid node editing

Success Criteria

Boardmesh succeeds if it can:

  • feel infinite and lightweight at first open
  • keep freeform drawing pleasant
  • support structured diagrams inside named canvases
  • make connectors follow object movement reliably
  • remain testable in pure Rust at the geometry layer
  • render correctly with and without GL
