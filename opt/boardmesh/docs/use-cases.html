Explanation

Practical use cases and benefits

Start with a question the drawing should answer. Give the agent the facts it needs, use selection to review the result, and export a clear handoff.

Review a software design

Goal. Explain where requests enter, where work happens, and where data lives.

Person. Describe the real components and select the part that needs discussion. Agent. Draw labeled boxes and lines, explain the selected component, and add the agreed missing step.

Benefit. Both participants can refer to exact objects rather than interpreting a paragraph differently. The editable result can change as the design changes.

Draw a local API, a worker, and a database using the component facts I provide.
Label each line with what it carries. Keep assumptions in a separate text area.
When I select a component, explain its responsibility before suggesting edits.

The agent must obtain repository or system facts from its other authorized tools. Boardmesh does not discover the architecture automatically. Ordinary lines also do not follow moved boxes automatically.

Explain an unfamiliar codebase

Goal. Give a new teammate a small map of the important modules.

Person. Choose the scope and point to a module. Agent. Use its repository context to draw the module map and explain the selection.

Benefit. The explanation stays connected to a visible map. The team can preserve the PNG and editable board with onboarding material.

Use the repository facts we have verified to draw the five modules a new
teammate needs first. Put file paths in labels. Separate observed behavior
from guesses. Explain only the component I select next.

Investigate an incident

Goal. Distinguish observed events from possible causes.

Person. Supply timestamps and evidence. Agent. Create a timeline with labels, use a separate color for hypotheses, and update it as facts are confirmed.

Benefit. The board makes disagreement and gaps visible. A PNG can accompany the incident notes without depending on the agent conversation.

Create a timeline from the events below. Use blue for verified observations
and yellow for hypotheses. Do not invent missing timestamps or causes.
When I select an event, list the evidence we still need.

Boardmesh does not fetch logs, retain incident evidence, or monitor services. Your agent client and your incident process provide those functions.

Turn a discussion into a plan

Goal. Separate the problem, options, decision, and next actions.

Person. Choose priorities and tradeoffs. Agent. Lay out the options, add labels, and export the agreed plan.

Benefit. People can compare alternatives in one view and keep the reasoning beside the chosen option.

Create three areas labeled Problem, Options, and Next actions.
Use rectangles and text from my notes. Leave uncertain items yellow.
Include our existing task IDs as text, and do not create or complete tasks.

Task IDs are ordinary labels. Synchronizing WorkMesh or another tracker requires a separate caller or integration.

Prepare a code review discussion

Goal. Show the changed path and the behavior a reviewer must assess.

Person. Select the risky boundary. Agent. Draw the before-and-after flow from reviewed code and put test evidence in labels.

Benefit. Reviewers can inspect the explanation without reconstructing a long chat. The board remains an illustration; source code and tests remain the evidence.

Draw the request flow before and after this change using facts from the diff.
Mark the boundary whose behavior changed. Put the relevant test names beside it.
Do not state that a test passed unless its output is available.

Review test coverage

Goal. Compare important behaviors with the tests that exercise them.

Person. Choose scenarios and acceptable gaps. Agent. Draw a small matrix with rectangles and labels, apply an agreed color convention, and highlight uncovered behavior.

Benefit. The team can discuss gaps visually. Actual test execution and results still come from the test tools, not from Boardmesh.

Create an asynchronous handoff

Goal. Leave a diagram that another person can understand and continue.

Person. Check that labels, questions, and next actions are clear. Agent. Export a PNG and identify the editable board files.

Benefit. The next person can view the picture immediately and reopen the JSON later. They do not need the original chat history.

Choose a good first use case

Start with one local person, one agent, and a small board. Check the collaboration conventions before attempting several writers. A clear five-object explanation is more useful than a large board whose labels and assumptions nobody has reviewed.
