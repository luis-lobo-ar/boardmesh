PRD-002: Semantic Links and Diagram Endpoints

Summary

Boardmesh should not expose only low-level connector primitives to users. On top of the connector math layer, it should offer higher-level semantic link objects with endpoint markers, routing heuristics, and diagram-aware defaults.

This layer should support:

  • general visual links and arrows
  • richer relationship semantics
  • ERD endpoint markers such as ||, o|, |<, and o<
  • future class, component, and workflow link families

The goal is better UX without contaminating the pure math/routing layer.

Problem

The new connector primitives in Boardmesh are necessary but not sufficient for good diagram UX.

Primitive connectors alone do not answer:

  • which sides of objects to attach to by default
  • when to use a straight line, elbow route, or spline
  • how to keep link movement visually stable while endpoints move
  • how to show semantic relationship ends such as ERD cardinality markers
  • how to expose diagram-friendly links without forcing users to think in raw routing geometry

Without a higher-level link layer, Boardmesh would behave like a low-level drawing tool with smart lines, rather than a visual modeling system.

Vision

Users should be able to create and edit links as semantic objects:

  • “link these two things”
  • “make this a one-to-many relationship”
  • “convert this connector into an ERD relation”
  • “keep this as a smooth dependency arrow”

Boardmesh should then choose sensible routing and endpoint marker behavior automatically, while still allowing manual override when needed.

Product Principles

  1. Semantic links are layered on top of connector primitives The math/routing layer remains reusable and renderer-agnostic.

  2. Endpoint markers are first-class Link ends must support independent semantics and rendering.

  3. Stable layouts beat clever re-routing Heuristics should prefer visual continuity when objects move.

  4. Diagram modes are additive Freeform drawing remains available even when semantic links are enabled.

  5. Human and agent parity Semantic link creation and inspection should be available in GUI workflows and exposed through MCP/runtime CLI where the action is meaningful programmatically.

Core Concepts

Link Object

A LinkObject is a user-facing relation with intent, styling policy, and endpoint semantics.

It wraps or resolves to a connector primitive for actual geometry.

Suggested fields:

  • link_id
  • kind
  • source
  • target
  • routing_preference
  • start_marker
  • end_marker
  • label
  • layout_hints
  • style

Link End

Each link end must be modeled independently.

A link end contains:

  • endpoint binding
  • marker type
  • optional label
  • optional side/anchor preference

Marker Families

Boardmesh should support marker families rather than a single hardcoded arrowhead.

Initial families:

  • none
  • arrow
  • bar
  • double bar
  • circle
  • crow’s foot one
  • crow’s foot zero-one
  • crow’s foot one-many
  • crow’s foot zero-many
  • diamond
  • filled diamond

Diagram Presets

Semantic links should support presets such as:

  • freeform arrow
  • dependency
  • association
  • containment
  • ERD relationship
  • inheritance
  • workflow transition

Each preset can map to:

  • default markers
  • default routing preference
  • default anchor policy
  • label placement rules

ERD Endpoint Requirements

Boardmesh should explicitly support ERD cardinality/optionality ends.

Examples of user-facing meanings:

  • || exactly one
  • o| zero or one
  • |< one or many
  • o< zero or many

Internally, these should be represented as structured endpoint semantics, not string glyphs.

Architecture

1. Primitive Connector Layer

Existing connector primitives and mesh-graph remain responsible for:

  • endpoint binding
  • anchor resolution
  • route generation
  • hit geometry

2. Semantic Link Layer

Boardmesh owns the semantic link objects and heuristics layer.

This layer is responsible for:

  • marker semantics
  • diagram preset selection
  • routing preference policy
  • default anchor selection
  • label behavior

Current Implementation Seam

The first production slice should keep semantic links intentionally thin:

  • LinkObject stores semantic source/target ends, routing preference, and labels
  • LinkObject resolves to ConnectorSpec through a pure conversion seam
  • scene storage, hit testing, bounds, and rendering reuse the existing connector pipeline

This keeps the current link layer testable and stable while later tasks add endpoint markers, presets, and routing heuristics on top.

3. Rendering Layer

The renderer should draw:

  • the resolved connector path
  • endpoint markers
  • midpoint labels
  • selection handles and editing affordances

Rendering should remain backend-agnostic.

Data Model Direction

struct LinkObject {
    id: String,
    kind: LinkKind,
    source: LinkEnd,
    target: LinkEnd,
    routing: RoutingPreference,
    label: Option<String>,
}

struct LinkEnd {
    endpoint: ConnectorEndpoint,
    marker: LinkMarker,
    label: Option<String>,
}

enum LinkMarker {
    None,
    Arrow,
    Bar,
    DoubleBar,
    Circle,
    CrowFootOne,
    CrowFootZeroOne,
    CrowFootOneMany,
    CrowFootZeroMany,
    Diamond,
    FilledDiamond,
}

UX Requirements

  • Users can create a plain link without selecting marker details first.
  • Users can upgrade a primitive connector into a semantic link.
  • Link presets choose sensible defaults for routing and endpoint markers.
  • Users can edit each link end independently.
  • Moving bound objects should preserve readable, stable link geometry.
  • Labels should have predictable defaults and remain movable later.

MCP and CLI Requirements

Programmatic surfaces should eventually support:

  • create semantic link
  • inspect semantic link
  • set link kind/preset
  • set endpoint markers
  • read resolved path and marker semantics

This should be additive over the existing connector primitive APIs.

Out of Scope for This PRD Slice

  • full automatic graph layout
  • crossing minimization across whole diagrams
  • advanced obstacle avoidance
  • per-diagram validation engines

Those can follow after the semantic link layer exists.
